# 직원 로그인 연결·최초 책임 관리자 등록

2026-10-11. 사용자는 인증 서비스 **아직 미정·연결 준비부터 진행**을 선택했고, 최초 개인 책임 관리자 이메일을 지정했다. 지정 계정 정보는 Git 밖 `.work/staff-auth-setup/pending.json`에 보관했다. 이름·서비스·클라이언트 설정·인증용 HTTPS 주소·실제 계정 소유 확인은 미완료이며 실제 staff 등록·활성화는 하지 않았다.

## 연결할 때 필요한 정보

| 설정 | 용도 |
| --- | --- |
| APP_ORIGIN | 인증용 HTTPS 사이트의 정확한 origin. 경로·사용자정보 제외 |
| OIDC_ISSUER | 확정 제공자의 Discovery issuer와 정확히 같은 값 |
| OIDC_CLIENT_ID / OIDC_CLIENT_SECRET | 해당 사이트에 등록한 OIDC 앱 설정. 비밀값은 로컬 `.dev.vars`/운영 비밀 설정에 보관 |
| STAFF_AUTH_RATE_SECRET | 최소32자의 별도 무작위 비밀값 |
| 초기 관리자 이름·개인 이메일 | 회사/사용자가 확인한 개인 계정. 단체 공유 계정 대신 개인 식별 |
| redirect URI | APP_ORIGIN + `/api/staff-auth/callback` |

현재 HTTP `127.0.0.1:8787`은 공개 페이지 제작 미리보기로 유지한다. 실제 직원 인증은 HTTPS 시험 주소·인증 서비스의 redirect URI 설정이 필요하다. APP_ORIGIN을 HTTP로 임의 설정해 로그인 검사를 우회하지 않는다. `.env.example`은 이름만 제공하며 실제 비밀값은 작성하지 않았다.

## 제공자 선정 후

1. 회사가 사용할 제공자/앱과 개인 계정을 확정한다. Google을 선택한다면 [Google OIDC 설정](https://developers.google.com/identity/openid-connect/openid-connect)의 앱 등록·동의 화면·정확한 redirect URI·issuer 설정을 적용한다. 이 문서가 Google 선택/클라우드 앱 생성/요금 승인을 뜻하지 않는다.
2. 제공자가 서명된 ID token에 `sub`, `iss`, `aud`, `iat`, `exp`, `nonce`, 확인된 `email`과 `email_verified=true`를 제공하는지 확인한다. 현재 초대 수락 계약은 확인된 이메일을 요구한다. Microsoft의 [ID token 표준 클레임 안내](https://learn.microsoft.com/en-us/entra/identity-platform/id-token-claims-reference)에서는 `email`/`preferred_username`만으로 확인된 이메일 소유를 단정하지 않는다. Microsoft 등 제공자가 이 계약을 제공하지 않으면 별도의 검증/연결 설계를 먼저 확정하며 검사를 생략하지 않는다.
3. 로컬 `.dev.vars` 또는 별도 시험 환경에 비밀값을 설정한다. `pnpm auth:check`로 누락 설정·HTTPS origin·issuer·Discovery·토큰 교환 방식을 확인한다. 출력은 비밀값을 표시하지 않는다. 이 확인은 실제 로그인 성공이나 클라이언트 비밀값의 유효성 검수를 대신하지 않는다.
4. 대상 로컬 DB를 백업하고 `pnpm db:local`을 적용한다. 개인 이름/이메일/회사 확인 여부(`accountConfirmed:true`) JSON을 **표준 입력**으로 전달하여 `pnpm auth:initial-local --create`를 실행한다. 이메일·토큰을 명령 인자로 넘기지 않는다. 이 명령은 로컬 DB 하나를 확인하고 트랜잭션으로만 실행하며 원격 DB/서비스를 변경하지 않는다. 원격 최초 등록은 별도 신뢰된 운영 절차에서 `applyInitialAdmin`을 같은 D1 batch로 호출해야 하며 공개 HTTP 경로로 노출하지 않는다.
5. 출력되는 일회성 초대 링크(48시간)를 개인 계정에서 사용한다. 초대는 수락 전에는 invited이고 세션이 없다. 서명/issuer/audience/state/nonce/PKCE와 확인된 이메일이 모두 맞아야 issuer+subject를 연결하고 active로 전환한다. 실제 성공 시 로그인 이력을 함께 저장한다.
6. 최초 등록 잠금은 유지한다. 수락 전 초대가 만료/유실되면 같은 확인 이메일 JSON을 표준 입력으로 `pnpm auth:initial-local --reissue`에 전달한다. 이전 초대는 폐기하며 이메일/역할을 바꾸거나 활성 계정을 다시 초기화하지 않는다. 일반 직원 초대는 책임 관리자 화면에서 다시 발급할 수 있다.

## 실제 검수 순서

초기 책임 관리자 로그인 → 직원별 역할 초대/로그인 → 콘텐츠 직원 문의 접근403·문의 직원 콘텐츠 접근403 → 겸임 직원의 직원 관리/삭제복구403 → 최신 역할 회수·계정 정지 즉시 반영 → 로그아웃/유휴30분/최대8시간 재인증 → 마지막 활성 책임자 회수 방지 → 허용된 화면으로만 복귀 → 제공자 오류/미설정 시 접근 폐쇄를 확인한다. 최초 책임자 첫 화면의 문의 업무는 아직 준비 중이며 관리 메뉴에서 직원/콘텐츠 관리로 이동할 수 있다. 문의 기능 완료를 뜻하지 않는다.

만료 flow·유휴/만료/폐기 세션·만료 요청 제한 레코드는 예약 작업에서 최대100건씩 정리한다. 직원 식별·초기 등록 잠금·초대/감사 이력은 지우지 않는다. 로그인/로그아웃/초기 등록 이력에는 직원 ID·종류·시각만 남기며 제공자 토큰·쿠키·초대 원문·비밀값을 저장하지 않는다. 실패 로그인 상세 운영 알림·이력 보관 정책은 추후 확정한다.

현재 자동/모의 시험 통과와 실제 제공자 검수를 구분한다. 서비스 선정·앱 등록 설정·HTTPS 주소·개인 계정 이름/소유 확인을 마치기 전에는 현재 로그인 화면이 준비 중으로 유지된다. 실제 사이트 배포·회사 기능 검수·오픈은 수행하지 않았다.
